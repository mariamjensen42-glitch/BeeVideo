# 依赖继续手工装配，不引入 DI 框架

引入每页一个状态持有者之后，页面不再直接 `new` 仓储，而是要求构造参数。
参考实现用 Koin，`docs/scope-and-m1-delivery.md` §5 也把 Koin 列为候选选型，
所以「要不要上 DI 框架」是一个真问题，而不是默认答案。

决定：**继续手工装配** —— `BeeApplication` 持有少数几个进程级对象，
每个状态持有者一个显式工厂。不引入 Koin / Hilt。

理由：需要装配的对象数量很少（4 个进程级对象 + 6 个页面持有者），
手工装配读起来是线性的，依赖缺失在编译期就暴露；
DI 框架会把它变成运行期的「谁提供了这个类型」，而本项目排在首位的失败模式
恰恰是**排查方向不明**（`SiteClientFactory` 那段「误导性报错比不支持更难排查」
的注释就是这条标准的样板）。

代价：每页一个工厂样板代码。若页面数增长到十几个，这条决定应当重新评估。
