## 「跟官方效果图差很多」的原因诊断（下午）

高城的反馈原话：「跟官方的效果图看起来差很多啊……一直没有那个味道」。
做了量化诊断，**结论：词汇用的是 M3，语法不是。**

### 方法（可复用）
1. `ui/` 里 grep 统计 `colorScheme.*` / `typography.*` / `shapes.*` 的实际引用次数
2. 用 `.workbuddy/scripts/png_probe.py` 逐像素分类截图，量各视觉元素的**面积占比**
3. `javap` 解出 alpha28 的 `classes.jar`，列类名确认**哪些 Expressive 组件可用但没用**

### 实测结果
- **面积**：琥珀强调色只占屏幕 **1.5%（详情页）～5.3%（首页）**；详情页 69% 是纯黑 surface；
  海报/其他彩块占 57.9%（首页）。→ 主题色几乎没有出场面积。
- **颜色角色**：`primaryContainer` / `onPrimaryContainer` / `tertiary` / `onTertiary` /
  `tertiaryContainer` / `onTertiaryContainer` 在 `ui/` 里**显式引用 0 次**。
  61 处颜色引用里 35 处是 `onSurface`/`onSurfaceVariant`（纯文字色）。
- **排版**：15 档用了 13 档，但**全部落在 11–24sp**；display 三档 + headlineLarge/Medium
  五档一次没用。labelMedium(12sp) 用了 11 次 —— 强调档加粗在小字上等于没效果。
- **形状**：只有 `shapes.medium`(12dp)×4 和 `shapes.extraSmall`(4dp)×1。
  Expressive 新增的 20/32/48/full 一档没用。
- **组件**：alpha28 里**有** `ShortNavigationBar`（短导航栏，`NavigationBarHorizontalItem`
  指示器 40dp、图标标签横排）、`MediumFlexibleTopAppBar` / `LargeFlexibleTopAppBar`
  （112→64 / 152→120dp）、`ButtonGroup`、`SplitButton`、`FloatingToolbar`、`Carousel`、
  `WideNavigationRail`。项目只用了 `LoadingIndicator` 一个。
  现在渲染的是基线下导航栏：**指示器实测 32dp + 图标在上标签在下**（= `NavigationBarVerticalItem`）。
- **海报配色**：`posterBrush(id)` 用 `id.hashCode()` 推色相（`HUE_STRIDE=47`），
  饱和 0.42–0.48、亮度 0.34→0.14 —— 屏幕上最大的一块颜色**在主题色板之外**，且暗端接近黑。
- **动效**：`MotionScheme.expressive()` 只影响读它的组件；NavHost 的页面转场走
  navigation-compose 自己的规格，**不吃这套**，所以换页手感是标准 M3。
- **色调体系**：中性色冷偏蓝（`surface #0B0B0D` B−R=2、`surfaceContainer #1A1A1F` B−R=5），
  与暖琥珀 primary 色相相反 → 主题色像"贴上去的"。

### 建议的动手顺序

## 执行（下午第二轮）—— 动手前的核对推翻了上面三条结论

高城说「执行」后，我先把上面每条结论对着 alpha28 的字节码复核了一遍，
**三条是错的**。教训：诊断阶段的推断必须先验签名再写代码。

### 更正 1：`androidx.compose.material3.Typography` 已公开 15 个 `*Emphasized` 角色

`javap` 出 `Typography` 的成员里有
`getDisplayLargeEmphasized` … `getLabelSmallEmphasized`（15 个），
**零个 `Experimental` 注解 = 稳定 API，不需要 opt-in**。

即：本项目手写的 `ui/theme/Type.kt`（15 档基准 + `BeeEmphasized` 15 档）是**把官方刻度抄了一遍**。
逐项比对后：除 `displayLarge` 字距抄成 −0.2sp（官方 +0.2sp，且本项目从未用到）外，
其余 tracking / lineHeight / weight 与官方 token **完全一致** —— 抄对了，但零视觉收益。

→ 处置：删 `Type.kt`、删 `BeeEmphasized`，`Theme.kt` 显式传 `Typography()`，
全站改用 `MaterialTheme.typography.<role>Emphasized`。

### 更正 2：基线 `NavigationBar` 在 alpha28 里已经是 Expressive 实现

诊断时以为「基线导航栏 = 老样式」，错。逐行读源码后：

| | 基线 `NavigationBar` | `ShortNavigationBar` |
|---|---|---|
| 容器高度 | `NavigationBarTokens.TallContainerHeight` = **80dp** | `NavigationBarTokens.ContainerHeight` = **64dp** |
| item token | `NavigationBarVerticalItemTokens`（指示器 **56×32**） | 同一套 |
| 指示器形状 | `NavigationBarTokens.ItemActiveIndicatorShape` = `CornerFull` | 同 |
| 标签字型 | `NavigationBarTokens.LabelTextFont` = `labelMedium` | 同 |
| 动效 | `MotionSchemeKeyTokens.DefaultEffects` + `FastSpatial` | 同 |
| 颜色 token | `NavigationBarTokens.*`（`ContainerColor`=surfaceContainer、`ActiveIconColor`=onSecondaryContainer、`ActiveIndicatorColor`=secondaryContainer、**`ActiveLabelTextColor`=secondary**、未选中=onSurfaceVariant） | 同一套 |

→ 所以两者**唯一可见差别是容器高度 80dp → 64dp**。
另外更正：`ShortNavigationBarItem` 默认 `iconPosition = Top`，用 vertical item token（56×32）；
那个 40dp 的 `NavigationBarHorizontalItem` 只在 `iconPosition = Start` 时才用，
而官方源码写明 `Start` 是**横屏手机**用的、`Top` 是**竖屏手机**用的。
本项目锁竖屏 → `ShortNavigationBar(EqualWeight)` + 默认 `Top`，正中。

顺带删掉了 5 个手抄的颜色参数：那些默认值**就是**规范值。

### 更正 3（新的，也没想到）：M3 顶栏的静止容器色是 `surface`，不是 `surfaceContainer`

`AppBarTokens` 解出来：
- `ContainerColor` = **surface**
- `OnScrollContainerColor` = **surfaceContainer**，`OnScrollContainerElevation` = Level2
- `TitleColor` = onSurface（**不是 primary**）、`SubtitleColor`/`TrailingIconColor` = onSurfaceVariant

即「顶栏恒 surfaceContainer」这个旧结论把**滚动后**的颜色当成了默认色。
正确行为是：静止时顶栏与 body 同色（看不出是一条色带），内容滚到它下面才浮起来。
之前菜单里也一直把标题手写成 `primary`，规范里顶栏标题就是 onSurface。

→ 处置：所有顶栏 **不传 `colors`**，吃 `topAppBarColors()` 默认值 + `scrollBehavior`。

### 附带查清：flexible 顶栏的 `nestedScroll` 该挂哪

读 `TopAppBarMeasurePolicy`：
```kotlin
val layoutHeight = (maxLayoutHeight + heightOffset).coerceAtLeast(0)
```
`heightOffset` 就是滚动偏移（≤0）—— 说明顶栏的**测量高度真的会随滚动变小**，
不是「布局高度固定、内部平移」。于是 `Scaffold` 的 `innerPadding` 每帧都在变。

> 推论：`nestedScroll(scrollBehavior.nestedScrollConnection)` 挂 **Scaffold** 上
> （官方 sample 的写法），挂滚动容器上虽然也能跑通，但语义上该由外层持有。

顺带：`TwoRowsTopAppBar` 是「固定 64dp 的小标题行 + 高度收缩的大标题行」两段 `Column`，
小标题的 alpha 走 `TopTitleAlphaEasing.transform(collapsedFraction)`，
大标题 alpha 走 `1 - collapsedFraction`，两行同时交叉淡入淡出。

## 浅色主题 + 海报刷子修复（晚间，装机双主题验证通过）

高城：「做个浅色主题啊」。

### 一、浅色方案（`Color.kt` 重写 + `Theme.kt` 一行）

`BeeVideoTheme(darkTheme: Boolean = isSystemInDarkTheme())`，两套 `ColorScheme` 并列。
显式暴露参数是为了 `@Preview` 能各自锁一种，不用改系统设置或跑两台机器。

浅色关键值（全部逐对验过对比度，正文级 ≥4.5:1）：

| 角色 | 深 | 浅 | 说明 |
|---|---|---|---|
| primary | `#FFC107` | `#7A5900` | 琥珀 tone 80 → tone 40；浅色下琥珀必须压暗才当得起文字色 |
| primaryContainer | `#5C4200` | `#F7C94F` | **不用 M3 默认的 tone 90**，见下 |
| secondaryContainer | `#4A4436` | `#DED0AC` | 同上，深一档 |
| surface | `#0B0A08` | `#FFF9EF` | tone 6 → 98 |
| containerLow…Highest | `#151311`…`#332F29` | `#FBF2E4`…`#E9E1D1` | 浅色下「越靠前的容器越深」，与深色相反 |

**为什么 primaryContainer 取 tone 84 而不是 M3 默认的 tone 90**：
黄源色的 tone 90（`#FFDF9E`）压在 surface(tone 98) 上对比度只有 **1.23**，
选中态剧集格等于看不出来 —— 这是黄色系在浅色方案里的固有问题。
取 `#F7C94F` 后对 surface 分离度 1.49，`onPrimaryContainer` 仍有 10.9:1。
`secondaryContainer`（导航指示器）同理：默认 `#EAE0CB` 对 surfaceContainer 只有 1.13 → `#DED0AC` = 1.31。

**媒体色不进 ColorScheme、两套共用**：`PlayerSurface`（播放器底恒黑）、
`PosterScrim` / `PosterTextPrimary` / `PosterTextSecondary`（图上文字必须自带对比度，
封面图的明暗与界面主题无关）。所以浅色主题只动了 `Color.kt` + `Theme.kt` 两个文件。

顺带删掉：`TextTertiary`（grep 确认只定义未使用）、`TextPrimary`/`TextSecondary`（只是 OnSurface 的别名）。

### 二、`posterBrush` 的两个真 bug（靠装机截图才发现）

**bug 1：散列失效，13 张海报同色。** 上一轮把 `(hash * 47) % 360` 改成 `hash % 1000`，
但没意识到演示数据 `v01..v13` 的 `hashCode` 只差 1，取模后 t 全挤在 0.935–0.968 —— 
**一整屏橄榄绿**。
修：先乘 Knuth 常数再取模，`(hashCode * 2654435761L) and 0x7FFFFFFF`，13/13 个 id 色相唯一。

**bug 2：暗端色相偏错方向。** 原来写 `hue + 12`，把深色那头推到 78–80°，也就是**黄绿色**；
L 已压到 0.18，黄绿在这个亮度区间读出来就是军绿。
修：改 `hue − HUE_SHIFT`，暗端走橙红方向。

**色带也顺手收窄**：`HUE_BASE 4f / HUE_SPAN 30f`（原 10/32）。
实测新截图上海报顶端色相落在 **3.8°–30.3°**，全部是砖红→铜色，橄榄角没了。

> 教训 1：`Color.hsl` 的实际渲染比 Python `colorsys.hls_to_rgb` **暗约 0.74 倍**
> （Compose 的 HSL 走的是自己的感知亮度模型）。**色相可对、亮度别信外部模型**，
> 要判亮度只能装机采样。
> 教训 2：改散列/取模这类「看起来等价」的推导，一定要拿真实数据集跑一遍分布，
> 别只看公式对不对。

### 三、可复用工具（新增）

- `.workbuddy/scripts/crop_zoom.py` —— 截图局部整数倍最近邻放大，肉眼看细节。
- `.workbuddy/scripts/ui_tap.py` —— **按文本/content-desc 定位并点击**。
  关键点：Compose 的文字语义叶子节点 `bounds` 常是 `[0,0][0,0]`（文字画在共享画布上），

### Ardot 画布踩坑（可复用）

1. **`C()` 的 `descendants` 覆写对普通 frame 不生效** —— 返回
   `Copy descendant not found: <新id>/<原descendant id>`，副本内容原样保留。
   正确做法：先 `C()` 建副本，再对副本子节点 `U()`。子节点 ID 通常 = 副本根 ID + 1（连续插入时）。
2. **SVG 里的 `<g transform="...">` 会让节点解析成 degenerate geometry**（整条 op 静默丢失）。
   改写绝对坐标 + `stroke`/`fill`，不要用 transform 缩放。
3. **Ardot 的 frame 默认 `clipsContent: true`**：子元素比父容器大就会被裁。
   实测「56dp 播放按钮塞进 48dp 高的行」被砍掉上下各 4px，`capture_layout` 报
   `Outside parent bounds`。行高要按最高的子元素给。
4. **绝对定位 + z 序 = 插入顺序**。要垫在已有子节点下面，得
   `M(新节点, 父, 0)` 手动插到 index 0。
5. **`layout: "wrap"` + `counterAxisSpacing`** 才是网格的正确写法（配固定宽 card、`hug_contents` 高）。
   列宽 = (可用宽 − gap×(列数−1)) / 列数。
6. `<ardot_image_gen mode="placeholder">` 的灰块**在深色主题里非常抢眼**（近乎纯白）。
   对策：在图片 frame 里再插一层 absolute 的深色底 + 自己的小标签，把占位灰盖掉。
7. `capture_layout` 的 `parentId` **不能传页面 ID**（报 "Root node must be a container, not a page"），
   要传每屏的根 frame。

## 顶栏滚动变色 → 恒定同色（高城反馈「上滑时顶栏背景和页面背景不一样，不好看」）

**根因**：五个页面的顶栏都没传 `colors`，全吃 `TopAppBarDefaults.topAppBarColors()` 默认值。
token 表里写死了一对：`AppBarTokens.ContainerColor = Surface`、
`OnScrollContainerColor = SurfaceContainer`。滚动时 `TwoRowsTopAppBar` 按
`overlappedFraction > 0.01` 在两者之间 lerp 出 `appBarContainerColor`，再用
`drawBehind { drawRect }` 画 —— 纯换底色。容器 elevation 是 `Level0`，
所谓「滚起来分层」并没有真实高度差，只剩一条横带。
浅色 `#FFF9EF → #F5EDDD`，深色 `#0B0A08 → #1C1915`。

**结论**：这次变色不承载信息。Scaffold 的 topBar 与 body 是上下相邻的两块，
body 滚动区有自己的裁剪边界，内容根本不会压到顶栏底下 → 取消。

**改法**：新增 `ui/components/BeeTopBarColors.kt` 的 `@Composable fun beeTopAppBarColors()`，
`containerColor` 与 `scrolledContainerColor` 都显式给 `MaterialTheme.colorScheme.surface`
（跟 `Scaffold(containerColor = ...)` 写同一个表达式，防止日后各自漂移）。
五个顶栏全部传入：首页 / 详情 / 收藏 / 设置 / 播放页。

**验证（装机实测，1080x2400 浅色）**：
- 首页滚动后 x=900 列 y 73..313 = `#FFF9EF`（收起顶栏区），与 body 的 surface 同值
- 详情页滚动前 y 0..520、滚动后 y 0..322 都是 `#FFF9EF`
- 归档图：`docs/screenshots/topbar_unified_home.png`、`topbar_unified_detail.png`

**API 细节（alpha28，javap 实测）**：
- `topAppBarColors()` 有 6 参数现行版（多 `subtitleContentColor`）和 5 参数 `HIDDEN` 弃用版；
  两者都**不带** `@ExperimentalMaterial3Api`，不需要 opt-in
- `MediumFlexibleTopAppBar` 的 `colors: TopAppBarColors` 参数存在且默认 `topAppBarColors()`

**顺带发现（未处理）**：`KeepScreen` 里还有一处 `widthIn(max = 320.dp)` 包在空态文本列上，
与「已删所有 widthIn」的记录不符 —— 空态文本封宽是合理的，但记录要记得更新。

**工具教训**：alpha17 的 `material3-android-*-sources.jar` 在 gradle 缓存里（alpha28 没下到），
查 API 签名用 `javap -v` 看常量池里的 `C(...)N(参数名:类型,...)` 字符串最快 ——
Kotlin 的参数名就藏在那条 source-information 常量里，比翻文档可靠。

## 首页加「精选横滑」hero moment（高城反馈「不够张扬，还是有点普通」）

**做了什么**：新增 `ui/components/HeroCarousel.kt`（M3 carousel 的 **uncontained** 布局，
项圆角 28dp / 项间距 8dp），作为**网格首项**（`span = { GridItemSpan(maxLineSpan) }`）接进首页。
同时对三条战术：36sp `displaySmallEmphasized` + 亮琥珀大色块 + 28/8dp 同心圆角，
和下方 12dp 圆角的海报网格正面对撞（M3 战术一：圆方混用制造张力）。

新增的东西：`strings.xml` 的 `home_featured_label` / `home_featured_meta`；
`BeeDimens` 的 `heroCardWidthFraction 0.82f` / `heroCardHeight 176.dp` /

**为什么是 carousel**：M3 对六种 carousel 布局的用途说明里，`Hero` 一类明确写着
「spotlighting very large visual items (**like a movie** or featured app)」。

**踩的坑（第二轮定稿，别回退）**：
1. 第一版卡片底用 `primaryContainer` → 深色下 tone30 的 #5C4200 压在 tone6 的

2. 改成 `primary` → 深色对了（#FFC107 对 #0B0A08 = 17:1），浅色又反了
   （浅色 primary 是 tone40 的 #7A5900，176dp 的深橄榄压在暖白上同样发闷）。
3. **根因**：M3 把「最高强调的填充」在两套方案里放在了**不同角色**上 ——
   浅色 primary=tone40 / primaryContainer=tone84；深色 primary=tone80 / primaryContainer=tone30，
   **两者的明暗正好对调**。所以按**亮度**挑而不是按角色名挑。
   定稿：`heroFills()` 用 `MaterialTheme.colorScheme.surface.luminance() < 0.5f` 判定，
   **不能用 `isSystemInDarkTheme()`** —— 预览稿是 `BeeVideoTheme(darkTheme = false)` 显式覆盖的，
   读系统设置会让浅色稿取到深色那一套。

| 深色 | `#FFC107` | `#5C4200` | `#0B0A08` | — |
滚动后顶栏区 y=250 仍是 `#FFF9EF`（无横带）；切到「动漫」分类后 hero 跟着换成
「纸上江湖 8.8」；logcat 无 FATAL。归档图：`light_hero.png` / `exp_hero.png` / `light_hero_filter.png`。

**API 细节（alpha28，javap 实测）**：
- `Typography` 的 15 个 `*Emphasized` 角色全部 public、**不带实验性注解**，

## 首页版面重做：衬线 brand 字体 + Hero 布局刊头（高城反馈「布局还是普通，用点别的字体，要有艺术性的意外设计」）

**参考依据**（全部来自 `m3-expressive` 技能，不是凭印象）：
- `typography.md`「Brand vs plain typeface」：scale 有两个**字体槽**，
  brand = display + headline（表达）、plain = body + label（可读），Roboto 是两个槽的默认值，
  「Replacing Roboto boosts brand expression」
- `typography.md`「Editorial treatments」：独立展示型时刻可以由字**主导整个屏幕**
  （「Type can freely dominate the screen」），靠更大的 display 字号 + 与
  motion/shape/color 组合构成产品级 hero moment
- `containment.md` carousel 六布局：`Hero` = "spotlighting very large visual items
  (**like a movie** or featured app)"，做法是「一个大的 + **sneak peek** 下一个」，
  并要求 **snap 滚动、一次翻一项**；**small item 宽 40–56dp**；item 圆角 28dp

**改了什么：**

1. **字体族**（`Theme.kt`）：新增 `BeeTypography = Typography().withBrandFont()`，
   只对 display + headline（含 6 个 Emphasized 变体）+ `titleLarge`/`titleLargeEmphasized`
   做 `copy(fontFamily = FontFamily.Serif)`。**刻度一个数没动。**
   - `titleLarge` 必须一起换：`MediumFlexibleTopAppBar` 展开态是 `headlineMedium`、
     收起态是 `titleLarge`，Compose 的 `TextStyle.lerp` **对不同字体族不插值**，
     两端不同族会在折叠过半时硬跳一下（装机实测确认同族后无跳变）
   - **改字体族前先查设备有没有该字形的注册**，否则静默回退、白改。
     实测：`adb shell ls /system/fonts | grep -i serif` 有 `NotoSerifCJK-Regular.ttc`，
     且 `fonts.xml` 里 `index="0..3"`（SC/TC/JP/KR）都带 `fallbackFor="serif"` → 中文能出宋体

2. **精选横滑：uncontained → Hero 布局**（`HeroCarousel.kt` 重写）。`LazyRow` 换成
   `HorizontalPager`（天然 snap），`PageSize.Fill` + `contentPadding = PaddingValues(end = 52.dp)`。
   新增 `BeeDimens.heroPeekWidth = 52.dp`，删掉 `heroCardWidthFraction`。
   片名 `displaySmallEmphasized`(36sp) → `displayMediumEmphasized`(45sp)；
   卡内加一条「刊头行」：左 `精选` 印章 + 右 `01/05` 篇次（新字符串 `home_featured_index`）。
   卡片高度 176 → 200dp。

3. **首页顺序与容器**（`HomeScreen.kt`）：外层 `Column` 拆掉，全页只留**一个**
   `LazyVerticalGrid`、四个整行项 —— **刊头 → 分类 chips → 版块标题 → 海报**。
   刊头提到 chips 之前（第一眼看的是内容而不是一行筛选胶囊）。
   新增 `SectionHeader`（衬线 headlineSmall 栏目名 + 无衬线 labelLarge 条数，
   新字符串 `home_section_count`），是全 App 唯一「两种字体族直接相邻」处。
   chips 的 `contentPadding` 从 `screenMargin` 改成 `0`（网格项已缩进过，否则缩进两倍）。

| 项 | 结果 |
|---|---|
| 卡片左边缘 | **16.0dp** ✓ 与 chips / 版块标题 / 海报网格在**同一条线**上 |

**两个坑，都靠量像素才发现（肉眼看不出来）：**

1. **屏宽是 392.7dp 不是 411dp**。按 411 估的 57sp × 5 字 = 285dp 看着放得下，
   实际卡片可用宽度只有 ~268dp，于是「山与海之间」被折成「山与海之 / 间」，
   一个孤字掉到第二行。降到 45sp 才稳（5 字 225dp、6 字 270dp）。
   **CJK 的 display 字号要按最窄机型反推字数，不能按拉丁经验估。**

2. **`HorizontalPager` 的 `contentPadding` 是「首末页各自的停靠位」，且同时决定
   pageSize**（实测 `pageSize = 视口 − start − end`；而**裁剪边界是 pager 自身的 bounds，

   - 传 16 → 卡片左边缘落在 32dp，与全站 16dp 栅格错位

   传 0 之后两个问题一起消失，M3 Hero 要的「左侧齐平 + 右侧一条预告」才成立。

3. 版本提醒：alpha28 里 `HorizontalPager` 已稳定，**不需要 opt-in**；
   `MaterialShapes`（35 个形状 + `toShape()`）和 `androidx.graphics:graphics-shapes`
   也都在依赖里，本轮**没有动用**（M3 说形状别用在文字密集容器上）。

## 第四轮 · 首页海报卡改版 + CatVod 协议调研

### PosterCard：从「盒子」改成「海报」

**症状**（装机截图）：13 张卡是 13 个扁盒子 —— 片名在图上压一遍、卡下又重复一遍，
整片没有横向节奏。诊断四条：底托让它像列表项、片名纯冗余、图上文字居中显得廉价、
13 张同一色相糊成一片。

**四个动作**：
1. 删掉 `Card` 的 `surfaceContainerLow` 底托 + 卡下那条重复文字行 → **卡片 = 一张图**
2. 图上文字从「居中」改成「**底部左对齐堆叠**」（片名 + 状态聚成一个块），
   评分印章留在左上，形成对角平衡
3. `posterAspect` 3:4 → **2:3**（经典海报比例）；详情页封面另立
   `detailPosterAspect = 3:4`（那边是横向并排布局，拉长会把信息块撑高）
4. 演示渐变的色相带 4°–34° → **8°–46°**，明度差拉大

**量到的数**（`png_probe`，密度 2.75）：
- 卡片宽 308.7px = 112.3dp，高 463px = 168dp → 2:3 正确
- 浅色下印章：高分 `#7A5900`(primary)、中分 `#7F5539`(tertiary) ✓

**踩的坑：双重压暗**
第一版把渐变暗端压到 L=0.16，**同时又叠了 0.96 的底部 scrim**。装机纵向剖面：
卡片走到 56% 高度就已经是 `#301611`（近乎纯黑），黑尾占 45% 卡高。
副作用不只是黑 —— **卡底那片黑是同一个颜色，它自己变成了新的「统一底色」**，
刚拉开的色相节奏又被它抹平了。
改法：暗端抬到 L=0.28、scrim 末端 0.96 → 0.62，起点 0.42 → 0.50。
片名处实测对比度仍有 3.3:1（M3 大字要求 3:1）。

**教训**：压暗层与暗端渐变是**两个独立的压暗来源，必须一起算**。
只调一个，另一个会把效果吃掉。

### 顺手修的

- `PRESSED_SCALE` 三处各写各的（0.95 / 0.95 / 0.96），其中 HeroCarousel 的注释还写着
  「与 PosterCard 同一取值，两处必须一致」—— 注释在说谎。统一提到 `BeeMotion.PRESSED_SCALE`
- `BeeBrandFont` 从 `private` 放开为 `internal`，让海报层能借 brand 字体做片名
  （只 `copy(fontFamily)`，刻度仍是官方角色）
- 删掉已无引用的 `posterOverlayPadding` / `cardTextPadding`

### CatVod 协议调研（为下一步接入真实数据源）

读了参考项目的 `com.corner.catvodcore`：

- **接口** `com.github.catvod.crawler.Spider` 的 `homeContent / categoryContent /
  detailContent / searchContent / playerContent` **全部返回 JSON 字符串**（不是对象）
- **配置** `{spider, sites[], lives[], parses[], rules[], flags[]}`；
  `site.type`：0=XML(XPath) / 1=JSON API / 3=csp jar；`api` 以 `csp_` 开头时后半段是类名
- **线路编码** `vod_play_from` 用 `$$$` 分隔线路名；`vod_play_url` 用 `$$$` 分线路、
  `#` 分剧集、`$` 分「剧集名 + 播放地址」
- ⚠️ **它的 `JarLoader` 用 `URLClassLoader`** —— Android 上跑不了（Android 跑 DEX 不是
  JVM class），那份实现只能跑 desktop。Android 侧必须换 `DexClassLoader`，且 app 内要
  **自带一份 `com.github.catvod.crawler.Spider` 基类**（jar 里的 `csp_*` 继承它，
  父加载器里没有这个类就 `NoClassDefFoundError`）；targetSdk 37 下 jar 必须只读
- `Api.kt` 里带 `lives`（直播）—— 本项目**不做直播**，解析时直接忽略该字段

## 接入真实数据源（CatVod 三类型全部打通 + 三个真 bug）

范围按高城拍板：**一步到位含 csp jar**，**用本地 mock 服务验证**。
结果：type=1 / type=0 / type=3 三种源在真机上端到端跑通，含详情与播放。

### 三个真 bug（都是"看着像数据没到、其实是代码"的类型）

**1. 首页刊头与筛选行永远看不见 —— LazyGrid 的锚点按 key 搬运**

现象极容易误判：海报 12 张、分类、评分、封面全对，**唯独最上面少两行**。
时间扫描（4s→50s）位置完全不变，说明不是加载时序。
`uiautomator` 里网格的**第 0 个语义子节点就是版块标题**（正常应是刊头），
且标题上沿距网格顶只有 contentPadding 的 12dp —— 一个 item 的间距都没有。

根因：`LazyVerticalGrid` 的滚动位置是「首个可见项的 **key** + 偏移」。
加载期间网格里只有 `section` + `loading`，锚点落在 `section`；
数据到达后刊头（200dp）与筛选行（32dp）插到它前面，锚点**按 key 把 `section`
重新钉回顶端**，整页被向上顶 264dp = 200+16+32+16。
修法：**刊头与筛选行两个 item 无条件进网格**（空列表时各自高 0），
锚点恒为第 0 项 `hero`，插入内容不再搬动它。

⚠️ 排查提示：这个 bug 的第一反应一定是"数据没到"，而日志会告诉你数据早就到了。

**2. `api` 被当相对路径解析，jar 源必然报"找不到类"**

`CatVodConfigParser` 对 `api` 一律 `absolutize(sourceUrl, api)`。
`csp_MockSite` 于是变成 `http://host/csp_MockSite`，`spiderClassName` 剥前缀剥不掉，
拼出 `com.github.catvod.spider.http://host/csp_MockSite` → 报「jar 里找不到类 …」，
完全没有指向性。
修法：**`api` 语义随 `type` 变** —— JSON/XML 才 absolutize，SPIDER/API 原样保留。
另在 `SiteClientFactory` 加一道兜底：类名里出现 `/` 或 `:` 直接报「api 不是类名」。
（同一类问题：顶层 `spider` 的 `url;md5;hash` 里只有第一段是路径，也补了 absolutize。）

**3. 缺字段时排版散架 —— 孤立的「分 ·」**

XML 源没有评分字段，`"%1$s 分 · %2$s · %3$s"` 忠实渲染出
`分 · 2026 · 更新至 12`：一个没有数值的单位。
修法：新增 `ui/components/MetaLine.kt` 的 `metaLine(...)`（空片段连分隔符一起去掉）
+ `scorePart(score)`（判断建在**原始值**上，格式化后再判会拿到 `" 分"`）。
三处替换：刊头元信息、详情顶栏副标题、详情信息行。`XmlSiteClient` 也改成
**有 `<score>` 就读**（XML 有没有这个字段两类都真实存在）。

### 其它修正

- **mock `/spider.jar` 稳定 404**：路由用了相对路径 `mock_spider.jar`，而服务是在
  项目根目录起的，jar 在 `.workbuddy/scripts/` 下。改成按 `__file__` 定位。
  这类失败在 App 侧只表现为「下载 jar 失败（HTTP 404）」，看着像没构建。
- `build_debug.py` 支持传任务列表（`clean assembleDebug`），用来排除
  "增量缓存给了过期产物"这类怀疑。
- mock 的 XML 模板**故意不给 `<score>`**，持续覆盖缺字段降级这条路径。

### 环境新踩坑

- **adb server 每次 Bash 调用都被回收**（每次都要重新 start-server），
  `adb reverse` 映射随之消失 → 任何需要 App 联网的操作**必须在同一次调用里**
  先跑 `adb reverse tcp:18080 tcp:18080`。
- Python 里解析 Windows 命令输出要 `encoding="gbk", errors="replace"`：
  `netstat -ano` 在中文系统下是 GBK，直接 `text=True` 会 UnicodeDecodeError。
- `taskkill /F /PID` 从 Bash 传参会被 MSYS 改写（`//PID` 无效），
  用 Python `subprocess.run(["taskkill","/F","/PID",pid])`。

## 第四轮：拿"真实的东西"压测（高城要求「去网上找几个有用的资源换上去试」）

### 先说结论：没有去找现成的配置源

搜出来的一水儿是「影视仓」「聚合全品类资源」那种仓库。**没挑、没筛、没推荐** ——
这直接违反项目红线第一条（不内置/不推荐/不分发内容源）。挑源推荐 = 从"播放器外壳"
变成"源目录站"，那条线一过产品性质就变了。

但"看看能不能真的获取到"这个诉求完全成立，而且**技术上能做得比随便找个源更狠**：
用**权威源码校准 mock** + 用**公开合法测试流**打真实网络。两条都做完了。

### 关键动作：去读 MacCMS 的源码，而不是信博客

`gh api repos/magicblack/maccms10/contents/application/api/controller/Provide.php`
拿 base64 解码（**别用 raw.githubusercontent.com，直连会被断连**）。
997 行，读出了三条**决定性**事实：

1. **第 125–129 行**：`ac=list` 的查询字段是**写死的**
   `vod_id, vod_name, type_id, "" as type_name, vod_en, vod_time, vod_remarks, vod_play_from`
   —— 只有 `ac=videolist` / `ac=detail` 才是 `$field = '*'`。
   ⇒ **`ac=list` 不返回 `vod_pic` / `vod_year` / `vod_area` / `vod_score` / `vod_play_url`。**
   （`type_name` 是空串**占位**，但第 182–184 行 `vod_json()` 会按 `type_id` 回查 `type_list`
   补真名 —— 实际有值。差点被那行 SQL 骗了。）
2. **第 240 行**：`ac=list` 时 `str_replace('$$$', ',')`；**第 219 行**：站点配了
   `api.vod.from` 白名单时，**videolist/detail 的 `vod_play_from` 也变逗号**。
   ⇒ 线路名分隔符**两种都真实存在**，而我只认 `$$$`。
3. **第 246 行**：`class` 只在 `ac != videolist/detail` 时返回。⇒ 想要分类只能走 ac=list，
   没有第二个选择 —— 这条把"首页必须用 ac=list"从偏好变成了硬约束。

附带：真实响应里 `limit` 是**字符串** `"20"`。

### mock 升级：让它"像真的一样烂"

### 环境与工具新坑

- **设置页来源 chip 是横向 `LazyRow`**：第 4 个来源（白名单站）**屏外时不在 a11y 树里**，
  `ui_tap.py` 直接报「没找到匹配节点」。要先 `adb shell input swipe 900 1367 120 1367 300`
